## Selected safe transition (PROPOSED, not implemented)

1. Keep old login routes, token issuance, Redux user state, stored customer cart and old scanner unchanged in Batch A. Do not globally add expiresIn and force customers to log out as the first scanner patch. Do not silently honor unsigned/forged/expired credentials on any new route.
2. Add a separately gated POST `/ai/multi-scan/session` before the existing prefix auth middleware in main routes/multi-scan.js. Both the existing multi-scan gate and a new session gate default false. The route is not implemented now. JSON remains small/bounded; credential fields are strictly typed and never logged. The old prefix auth cannot run before password-based scanner issuance, and a new-file autoload race must not decide which handler wins.
3. New credential service uses explicit/lazily supplied model handles only after gating and with bounded scoped queries. It must not call existing login controllers: they import DB/cache modules, issue no-exp tokens and return broad error strings. models/user.js:3 imports dbconnect/gratis.js, whose createConnection and connection-string logging are side effects; disabled module import must not load them. Offline construction uses declared repository interfaces, not require-cache/global monkey patches.
4. After actual credential proof, use current Stage 7 tenant/role resolution, require unique identity, and sign a new token with dedicated scanner key (not the legacy key or AI HMAC key), explicit HS256, sub, email, iat/exp (900 seconds), iss=`cosmic-clavstore-scanner`, aud=`clavstore-multiscan-review`. Bind storeId/packageId claims to the selected context; new request handlers compare verified claims with current grant because Stage 7 itself derives scope from the request selector and does not enforce arbitrary scope claims. No grant may be fabricated to satisfy the WeakSet.
5. Keep scanner token in wrapper memory only; pin API base and scope, clear on expiry/logout/user/store/reseller change. Do not reuse MultiScanPosPanel enabled with user.token: that remains the incompatible legacy credential. No silent refresh from an email decoded out of an old token, even if legacy pages accept it.
6. Production security of existing decode-only routes, old password storage and order-derived credentials is a separate **BLOCKED** remediation. A legitimate-session-preserving global transition would cryptographically verify legacy signatures first, require re-login where identity/purpose/lifetime cannot be established, stage a bounded deprecation deadline for cryptographically valid old sessions on legacy routes only, and issue fresh credential-proven tokens. It must never relax scanner exp checks or grandfather forged tokens. No such global migration is included in 11-B's narrow batch.

First protected-file approval: **main routes/multi-scan.js only**, for this gated issuer registration. No existing auth/controller/middleware/client file is authorized by that proposed batch. New service/handler/repository/config/tests must be enumerated in its PR; keys/environment values are not provisioned or changed by source-edit approval. No database schema migration or dependency installation is required for the selected short-lived-session design. Global password/refresh/revocation migrations are outside it.
