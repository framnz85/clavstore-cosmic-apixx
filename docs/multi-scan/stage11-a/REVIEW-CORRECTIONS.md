# Independent corrections and acceptance decisions

Stage 10's documents were reviewed as proposals, not trusted implementations. The following are specific changes to its reasoning, without editing the earlier documents or source.

1. **JWT migration scope:** do not begin by changing all existing sign sites. Login, MD5-equivalent login, registration, app login and order-derived tokens have different purposes. A dedicated password-proven, purpose/key/issuer/audience/scope-bound scanner session is narrower and preserves legacy users' cart/session state. Existing decode-only middleware remains a critical independent production-security blocker, not a safe grandfathered authentication mechanism.
2. **No production-model import in disabled/offline construction:** actual models/user.js:3 imports dbconnect/gratis.js; that module creates a connection and contains connection-string logging. Explicit model handles are necessary and obtaining them must not occur merely by requiring an auto-discovered disabled route. This source fact is stronger than assuming Mongoose schema imports are harmless.
3. **Default router actually used:** server.js auto-loads the module export, not an arbitrary new call to createRouter(options). A newly configured factory sitting elsewhere does not wire anything. Select an explicit main router edit; importing a new route with a colliding prefix can fail behind the old gate/auth/parser. A nonoverlapping small-JSON route may work without a protected edit only when these conditions are proven and registration itself is approved.
4. **Raw upload bridge is composable, not production validation evidence:** Stage 10 encodeOrientedRgb can preserve frozen Stage 2 orientation/dimensions and feed Stage 7. It may expand beyond the encoded cap. It does not resolve HTTP parsing, authentication, cancellation ownership or live runtime behavior by itself; full decode still occurs at the upload and detector layers.
5. **Pin format is not an approved pin:** Stage 7 versions() accepts correctly shaped revision/checksum strings; probe P05 confirms no full allowlist comparison at that main boundary. AI loaders pin their own models, but Stage 11-B needs exact trusted deployment tuple conformance before exposing a scan. Policy/OCR/preprocessor/Yolo pins need the same explicit review.
6. **Detector truncation differs from crop truncation:** Stage 10's requireCompleteReview only rejects CROP_LIMIT_APPLIED. Probe P06 confirms detector.quality.truncated/candidateLimitApplied can be discarded in validateResponse, and its resulting current review passes the Stage 10 guard. Do not lower detector cap to ten and assume the guard knows extra objects were dropped. Add a raw conformance boundary and fail incomplete photos before any selectable result.
7. **Stage 9 is not a production composition factory:** it imports fixed synthetic fixture scope/keys, creates temporary indexes, uses captured admin grant and optional controlled rectangles. Its textual /tmp check is not canonical confinement (P08). Retain it as offline evidence and build a new explicit production composition, with no current index rebuild or format changes. Fail-whole-scan is the safe first production partial-failure policy unless the optional unknown/sibling adapter is separately reviewed.
8. **Catalog metadata bridge is a real missing interface:** receiver forwards signed tenant/user/role and scanId/topK, not a main opaque grant or snapshot callback. A captured fixture admin grant is not service authorization. BACKEND-AI-REVIEW.md proposes a bounded immutable sidecar release unit, same tenant/revision/generation pair and trusted provenance; a reverse catalog service would need its own authentication contract. Until one is approved/tested, end-to-end staging stays blocked.
9. **Full cart projection is not provided by Stage 7 current DTO:** product projection omits slug (P07), and there is no current text search method. Stage 9 returns fixture rows and defaults its authoritative cart to empty. New store-scoped public search/review projection must include actual current slug and minimal required POS fields, exclude cost/secrets, reject waiting links/duplicate special cart lines and bind real user/cart/scan provenance. Do not infer this from existing action-creation tests.
10. **Remote native lifetime is not main request lifetime:** main HTTP timeout/transport settlement cannot prove the AI native call finished. Stage 2 capacity releases on close, while the native operation may continue. Place native admission/drain/watchdog at the actual AI owner; main IO admission is separate. Preserve the AiClient's bounded/uncooperative transport behavior, but do not call it a remote-native completion guarantee.
11. **Stable error mapping needs explicit work:** AiClient at stage7/client.js:12 maps most non-2xx statuses, including receiver busy 429, to AI_SERVICE_FAILURE/502 (503/404 become AI_UNAVAILABLE). Therefore Stage 10's proposed end-to-end public 429 is not already implemented. A new declared safe transport adapter can use exported nativeTransport and map only whitelisted upstream statuses into typed errors while retaining fixed URL, TLS/DNS pins, HMAC and no recognition retry. Alternatively accept a documented sanitized unavailable result for initial staging; do not claim exact 429 behavior without tests. No existing transport object is patched in this stage.
12. **Frontend access is more than App.js:** a disabled route alone is not a POS link or scanner credential boundary. The minimal POS-access set is App.js plus one PointOfSale.js link insertion, with new wrapper modules and the flag false. Existing AdminRoute navigation is not a server-auth guarantee and may render before redirect. New wrapper must block network/camera until scope/credential readiness. API host selection and legacy global error/cart clearing cannot be reused indiscriminately.
13. **Warnings and manual corrections:** frozen normalizeScan drops global reasons; new API conformance must reject critical incomplete scans. Manual search target/results can outlive a rescan, and conservative potential stock across all candidate alternatives can block a valid explicit subset. These are testable UX/fail-closed limitations; do not silently auto-select or override stock to make the demo pass.
14. **Historical tests and benchmarks are not new readiness:** 428 retained tests and Stage 6/9 synthetic timings do not prove current device/TLS/deployment/grocery behavior. Eight Stage 11-A probes only inspected pure/fixture interfaces and exposed limitations. All real grocery accuracy and InterServer capacity claims remain blocked/unverified. No rollout/mutation/host access is approved.

No selected 11-B edit requires a schema/index-format migration or new dependency. Normal declared factory/client/provider composition in new modules is proposed; monkey-patching module exports, global runtime state, route order, DOM or authentication is not. The four selected protected paths form the future A/B/C union, not a single blanket approval. The first A approval contains one router file only.
