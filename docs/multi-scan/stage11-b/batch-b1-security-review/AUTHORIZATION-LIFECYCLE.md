# Scanner authorization lifecycle and freshness — proposed architecture

## Issuance sequence

1. Default-disabled main/session gates and configured dedicated key/issuer/audience, before DB/status acquisition. Keep all missing/malformed flags disabled; no provisioning or activation now.
2. Validate exact password-proven issuance request; reject legacy authtoken/tenant headers and unverified/expired/forged optional scanner Bearer. Use canonical typed store selector, never tenant proof. Fresh plaintext password against unique scoped User row; never client digest, decoded legacy email or cached profile upgrade.
3. Derive verified subject from current unique row; retrieve the independent policy keyed by that User._id from trusted connection. Require known schema, active state, canonical reseller, current version and explicit grant for requested store/action. Missing/unavailable/malformed status503; known denial401/403. Legacy deletion request adds denial; absence is not activation.
4. Require current primary/secondary User membership AND independent approved grant, current active Estore, equal current user/store/policy reseller id, active reseller parent, expected current global role and operation allowlist. Non-admin still needs current store orders permission. Any ownership/role/reseller drift denies pending reconciliation. A billing Package record, superAdmin flag or browser headers never substitutes for approved scope.
5. Re-resolve policy/current identity and scope after awaits. Sign a <=900-second HS256 scanner JWT with existing strict sub/email/iss/aud/iat/exp/storeId/packageId contract AND a NEW proposed authorizationVersion claim bound to the current policy version. Exact new claim name/validators and necessary Batch A source deltas require separate approval; this is not an existing token field. Current Batch A modules must not be silently changed to issue it.
6. Authenticate final subject/scope/current authority/version again before response and recheck expiry after asynchronous work. Return only scanner token, expiry, public scope and UUID. No raw user/policy/password/hash/service credentials. Tokens never confer cart/persistence/index-rebuild rights by default.

## Every subsequent scan/review request

Require cryptographic signature, HS256 allowlist, strict issuer/audience/mandatory bounded expiry/iat/sub and signed store/package/authorizationVersion. Tokens missing the new version at cutover fail401; do not grandfather existing scanner/legacy tokens. Resolve the exact current independent policy by verified sub, compare token version to current version, require active state and allowed store/action, and verify current User/Estore/reseller/role/permissions. Do not trust claims as current role or current membership. Do not reuse an old verified grant forever, cached policy, status-only observedAt response or global mutable tenant context.

Recheck after long inference/catalog awaits and immediately before publishing any selectable review output; Stage7 revalidate checks expiry before an await, so the future boundary must also check expiry/version after awaits. Drop results on revoked/deleted/missing/changed authority or expiry; do not return a partially selectable review as success. Recheck again for every later products/review operation and any future persistence boundary (not authorized here). No authorization state is derived from cart contents or client acknowledgment.

## Revocation and concurrency guarantees

Protected writer CAS increments principal version on disable/revoke/reenable, role/grant/ownership/member/credential change. Old tokens never become valid again merely because state returns active or a removed store is readded. A current-store permission denial is enforced even before policy reconciliation; wider grants require independent attestation/version change. Missing user/policy/store and DB failures fail closed.

A current final policy read has a defined linearization point. If revocation commits BEFORE that final authority decision, the request must deny and discard computed output. If it commits AFTER that decision, an already admitted operation may physically finish its response; do not promise zero response bytes after a concurrent commit from ordinary reads or snapshots. Fresh subsequent requests must see the new epoch and deny. Tests must exercise both orderings with explicit barriers. A stricter global no-completion-after-revocation guarantee needs a separately designed distributed fencing/lease protocol and writer/consumer coordination, not just a shorter TTL or callback timestamp.

Do not assume snapshots alone solve this race, or that a client abort proves underlying native work stopped. Existing admission remains held until true settlement; timeout or policy loss closes new admissions and prevents stale output. Native AI cancellation/ownership integration and response fences are future scoped review.

## Why prior B.1 adapter v2 is insufficient by itself

It checks existing handle identity and per-user active/disabled/revoked status, and preserves ambiguous user rejection, but its identityStatus DTO contains no scoped grant or policy epoch and cannot add the new signed version to Batch A issuance/consumers. observedAt freshness only timestamps a decision; it does not prove trustworthy role writes or eliminate stale authorization. Do not implement or activate it unchanged as the completed security foundation. Required future protected paths/interfaces include session-service/handler/factory/repository composition and every scan consumer; exact hunks wait for approved authority schema, writer and lifecycle policy. This review only proposes architecture and two independent evidence-backed containment/logging diffs.
