# JWT compatibility and migration

**Existing issued tokens cannot safely be upgraded into scanner sessions.** Source evidence: controllers/auth.js loginUser (email + MD5(password), jwt.sign without expiry options) and loginUserByMd5 (client hash comparison, jwt.sign without expiry options); controllers/user.js registration and controllers/app/user.js similarly omit bounded expiry; controllers/order.js issues an order-derived email token. Main middlewares/auth.js uses jwt-decode, not signature verification. No refresh/rotation flow was established by this review. Actual deployed credentials and active JWTs were not accessed.

Stage 2 multi-scan auth verifies HS256 but does not require exp/iat/issuer/audience. Stage 7 Security.verify requires valid email, bounded integer exp/iat, clock/age/lifetime checks and configured issuer/audience; it must not be relaxed. Existing optional legacy `aud=clavmall-estore` is not the new purpose audience. Signature correctness alone cannot supply missing expiry or fresh credential proof.

The proposed NEW contract follows Stage 11-A: distinct configured server key, HS256 only, issuer cosmic-clavstore-scanner, audience clavstore-multiscan-review, 900-second maximum lifetime, standard sub/email/iat/exp/iss/aud and explicitly proposed storeId/packageId claims. Key and issuer/audience environment names in the module specification are new configuration proposals, not existing provisioned values. They need approval and secure provisioning later. No fallback to JWT_PRIVATE_KEY or service/HMAC keys. Configuration also rejects reuse of any same-valued environment key/secret/token variable; deployment must independently attest key purpose separation beyond environment visibility.

Credential proof uses existing MD5 storage only for compatibility, bounded lookup by exact email plus selected primary/secondary store, unique row and constant-time digest comparison. It never accepts client MD5 as equivalent proof or reads showPass. This does not modernize weak legacy password storage. Unsupported/ambiguous credential records fail authentication; unknown/missing current tenant authority never yields a session. A future password hashing migration is a separate project.

Cashiers keep their existing POS login/cart. To access the future review scanner, request fresh typed password proof over approved HTTPS, obtain a dedicated token, retain it only in memory, pin the API base and selected store, and clear only scanner state on expiry/store change/logout/401. No global userToken replacement, cart clearing or automatic legacy-bearer replay. Omit legacy authtoken and tenant headers at issuance; body storeId is a selector checked against current records. Optional Authorization accepts only an already valid scanner-purpose token and still requires password proof. Missing Authorization plus valid fresh credentials succeeds; missing credentials fails 400.

Migration sequence: approve the exact disabled code/contract and isolated fixture schema; implement and run the planned tests in a later authorized batch; resolve trusted source composition and observed reseller relationship; approve distinct secret provisioning/issuer/audience plus ingress limits/rate/logging policy; separately approve Batch B consumer composition/scope revalidation; separately approve frontend memory-session wrapper; validate on authorized staging; only then separately authorize activation. Roll back by closing server admission and let 900-second tokens expire or explicitly revoke the dedicated key under separate authority. No silent compatibility switch, no no-exp tokens, no global login issuer edits and no persistent session/refresh schema.

**BLOCKED for activation:** trusted production model handles and actual authorization data semantics are not verified; no key is provisioned; optional-header contract and proposed claims need approval; consumer wiring is excluded; global parser/ingress, distributed rate enforcement and logging review remain unresolved. The preview is complete; production readiness is not claimed.
