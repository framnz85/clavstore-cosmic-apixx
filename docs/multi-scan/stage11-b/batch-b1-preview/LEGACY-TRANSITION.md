# Legacy-token transition — design only

Source-verified: controllers/auth.js loginUser signs email (optional legacy clavmall-estore audience) without bounded exp; loginUserByMd5 accepts a stored-digest-style credential; controllers/app/user.js, registration in controllers/user.js and order-derived signing in controllers/order.js also lack the dedicated scanner contract. middlewares/auth.js decodes rather than cryptographically verifies. None is valid proof for scanner identity. No active deployed JWT/key was accessed.

Recommended existing Batch A path: a cashier with an old POS session explicitly supplies fresh plaintext password, exact email and selected storeId to POST /ai/multi-scan/session over separately approved HTTPS. Legacy authtoken/tenant headers must be omitted; optional Authorization is only an already valid scanner-purpose token and never replaces password. Unique scoped credential proof, current active membership/reseller/role checks, required new authoritative identity decision and dedicated HS256 issuer/audience/expiry/sub/store/package checks produce the dedicated token. No token is issued when trusted authority is absent. Old decoded email, client digest, expired token or unsigned token cannot be exchanged for scanner access.

No existing login/refresh-token issuance change is needed for this password-proven path. There is no source-verified refresh/rotation mechanism to reuse. Current API composition lacks trusted sources and remains503 when authority is unavailable; the proposed adapter does not make the path live. Identity-disable policy and integrity of role/membership writes must be resolved first. Password reuse against legacy MD5 storage is compatibility only; do not read showPass or claim password storage modernization.

Future frontend scope: explicit password prompt, pin main API and selected tenant, retain scanner token only in memory, clear scanner-only state on expiry/401/store change/logout, require fresh proof on reentry; do not replace userToken, globally log out POS users, clear carts, replay old bearer tokens or forward AI credentials. Current UI integration is not proposed here.

If a later decision instead requires global shared-token/refresh migration, separately review controllers/auth.js (loginUser/loginUserByMd5), controllers/app/user.js (login), controllers/user.js (registration/signing), controllers/order.js (order-derived signing/purpose isolation), middlewares/auth.js (signature/purpose/expiry verification), and the actual frontend token/session wrappers. Add a refresh flow only under its own explicit schema/storage/rotation/revocation proposal. Blindly adding exp or scanner audience to every existing issuer could break unrelated sessions and would not solve unsafe role assignments. No global issuance/refresh edit is part of the minimum recommended B.1 adapter proposal; no speculative unified diff is supplied for that alternative.

Keep dedicated scanner key/issuer/audience provisioning, ingress/parser limits, logging/redaction, rate coordination and live staging authorization separate. Never relax Stage7 verification to accommodate no-exp legacy tokens.
