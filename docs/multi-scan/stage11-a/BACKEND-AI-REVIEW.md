## Routing, request and response boundaries

Main server.js:17 installs global JSON 2 MiB; :50–52 mounts each routes entry under `"/" + API_ROUTES`. AI server similarly mounts under configured API_ROUTES. External deployment base/path values were **NOT VERIFIED** and were not printed. Preserve that base in any proposed early AI mount; mounting only a bare `/internal/...` outside the configured application base can break fixed client URLs. Middleware must pass the canonical router path expected by the HMAC verifier rather than originalUrl including deployment prefix/query.

Main routes/multi-scan.js:19 applies gate → 32 KiB JSON limit → Stage 2 HS256 auth/resolver to the entire `/ai/multi-scan` prefix. The new password issuer must be deliberately before this chain with its own gate/rate/schema checks. New scan/search/review must use the dedicated Stage 7 verifier, not run through the legacy-key verifier first. Changing a factory option in a new file does nothing unless the actually exported default router is composed at the explicit registration point. The catch/fallback at :29–33 must remain safe when optional scanner configuration is absent/invalid: disable the new route, do not break old startup or silently activate legacy behavior.

Stage 2 scan controller cannot merely call Integration.scan as a current scan adapter: it passes flat tenant and raw photo, not original signed token/verified grant; reduces rich candidates and generates another scan ID; requires recordScan/authorizeProducts hooks; confirm emits confirmed:true. New handlers must retain Stage 7 scanId/requestId, rich DTO, reviewRequired and no-order/no-cart flags. Old controller and confirm should remain unused for the new feature; keep it unmodified to preserve frozen tests.

Upload is multipart **photo**, files=1/fields=0, MIME/container single-frame JPEG/PNG/WebP, default <=10 MiB, <=24 MP, max dimension 10000, upload timeout 15 s (services/multi-scan/upload.js:11–51 and contracts.js:14–25). Runtime is isolated multi-scan-runtime/node_modules, lazy at request time. Stage 7 imageBuffer is a bounded container sniff, not a full decoder. Use frozen upload validation + new bridge, then actual Stage 3 decoder; never treat sniff alone as validation. Return/validate actual oriented image dimensions and preserve coordinate space; do not downscale silently on server.

Stage 7 Integration.scan authenticates again, creates UUID, invokes fixed AiClient recognize, validates untrusted response and current catalog. It has no authenticated search, durable scan registry or cart confirmation API. Register scan ID → tenant/user/session/snapshot context with TTL in new explicit handlers before exposing any review. A new public-interface client facade may validate raw envelopes and associate server-owned scan IDs with the current request context; this is normal declared composition, not mutation of exports, require cache, routers or hidden hooks. Never fabricate an opaque grant or reuse an admin user's old grant for a cashier.

Search returns only authorized current catalog candidate fields. Review accepts exact IDs/counts and a bounded cart fingerprint; it is a review DTO, not a persistence instruction. Bind scan to user/tenant/expiry; define separately authenticated manual-search provenance for `manual-review`. Stage 8's browser fingerprint is JSON of the whole cart, not a trusted version or server permission. Enforce request byte limits and redact it from logs. Load authoritative cart for the real subject, reject duplicate/special lines or handle through existing POS, and use a minimal current public product projection including slug. No supplier-cost/password/showPass fields should be returned just because Stage 9 cloned a fixture row. No DB schema migration is needed for a bounded, single-worker review-only registry; restart invalidates review contexts and requires recapture. Durable registry/idempotency is a later explicit design.

## Chosen production composition direction (PROPOSED, still blocked)

Use Stage 7 main Security/Catalog/Integration with explicitly constructed model/repository/client interfaces. Use new AI worker composition of Stage 3 Detector, Stage 4/5 independent IndexStores/Recognizers, CombinedRecognizer, Stage 6 OCR/Reranker/CropPipeline/ScanPipeline and Stage 7 receiver. No Stage 9 fixture keys, hardcoded identities, synthetic boxes or temporary-root assumptions in production modules. Imports are inert and feature-gated before obtaining real model handles. models/user.js imports dbconnect/gratis.js which immediately creates a connection and logs a connection-string template; importing an existing production model in an offline test is prohibited and disabled startup must not introduce that import.

The unresolved main↔AI catalog metadata bridge needs an explicit implementation contract. The current receiver only forwards tenant + signed principal userId/role and scanId/topK; it does not forward an opaque main grant, browser JWT or snapshot object. Stage 9's in-process callback to Catalog.metadata using a captured fixture admin grant cannot become a network deployment by itself.

Smallest proposed staging direction: a versioned **read-only metadata sidecar** for the same authorized snapshot revision as the two existing index generations, exported by a currently authenticated admin using Catalog.indexingSnapshot/metadata in <=200-ID pages. Sidecar tenant, revision, content checksum, expiry/age policy and the two generation IDs must be pinned/approved as a release unit; metadata contains no prices/stock or user token. Publish through an explicitly authorized artifact operation, not an automatic browser scan rebuild. New AI metadata provider returns only requested IDs from the exact scope/revision after the trusted receiver capability has authorized the request. Main still reloads current active products/prices/stock before returning. This adds no existing index-format or DB schema change. The export/import protocol, content verification and artifact signing/pinning tests must be reviewed before usable staging; no export, copy, build or new sidecar was executed in 11-A.

Alternative is a separately authenticated reverse catalog service, but it needs new fixed-path auth, current request/grant binding, timeout/replay/cancellation design; do not assume existing AiClient exposes that operation (it only supports recognize/status). Do not give AI production DB credentials or substitute an always-admin authorizer. If neither bridge is approved, keep full E2E **BLOCKED** while Batch A/B pure components can be tested offline.

## AI contracts and lifecycle

- Stage 3 detect accepts encoded Buffer or strictly oriented raw-rgb; returns tenant/scanId/detection IDs, source XYWH boxes and PNG crop Buffers. Detector creates all bounded returned crops **before** Stage 6 slices to ten, so ten recognized objects is not ten generated crops or a memory cap by itself.
- Stage 4/5 embed accept encoded crop Buffer, lazily verify/load CPU sessions, reuse one session per worker and close explicitly when inactive. Separate model keys/dimensions (768/384), independent HNSW generations and a matching catalog revision are required. IndexStore authorizes before work and on search, validates paths/manifest/file checksums and supports validated fallback generation. Fallback/recovered generation still needs matching metadata, not the latest catalog page.
- CombinedRecognizer executes sequentially, validates each result against its own embedder metadata, and rejects mismatched SigLIP/DINO catalog revisions. This is stronger on AI than Stage 7's main-side format-only pin check, but does not establish the approved release allowlist at main.
- Stage 6 OCR has single active worker, per-crop pixel/region/byte limits, native calls and text/rotation warnings. Reranker requires authenticated tenant metadata at the returned index revision; it returns uncalibrated evidence, unknown/conflict status and acceptanceAllowed=false. It never authorizes price.
- Frozen CropPipeline aborts whole call on an inference/OCR exception. Stage 9 ResilientCrops can return an explicit unknown with the same ID for two named inference errors; it remains fixture-bound. Initial new staging worker may fail the whole scan safely; partial sibling recovery is an additional explicitly tested adapter choice, not a behavior already provided by the frozen pipeline.
- Native abort checks occur around awaits; cancellation does not interrupt every native inference immediately. Close methods reject busy workers. New worker owner must drain or terminate and await exit, not free slots on response close. A failed construction also needs finally cleanup of any sessions/index handles already initialized; Stage 9 factory success-close does not prove all production partial-init paths.
- Snapshot revision excludes live price/stock; current resolution fingerprint is different data and cannot be directly compared to an index revision to infer stale pricing. Keep exact immutable metadata revision for ranking and re-read current catalog for review. Enforce artifact age/current packaging policy separately.
